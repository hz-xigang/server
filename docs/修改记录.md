## 第 1 部分：打印纸箱标签（ProdTag）

### TAG-2【可选】事务先提交、后打印 PDF

- **位置**：`ProdTagService.add()`（`pmt.commit(status)` 在 `generateExcel()` 之前）
- **问题**：PDF 生成失败时标签已落库（ProdTag + PrintLog），前端重试会生成重复标签
- **现状评估**：先入库后打印、失败走补打，业务上可接受；若后续无补打流程则需处理
- **建议**：打印前按 tagNo 查重；或先生成 PDF 再提交事务（改动后需验证回滚路径）

### TAG-3【中】flag=2 用入库流水表判断"已入库"，与防重复规则不一致

- **位置**：`ProdTagService` / `ProdTagController` 的 `findVoByTagNo` 分支
- **问题**：`stockInTag` 是入库流水，同一 tagNo 可有多条（首次入库+退货入库+调拨入库）。用 `stockInTagPlusService.assertNotExists` 判断会导致：标签已出库（deleted=1）后再入库被误拦
- **文档规则**：防重复 = `StockInventory.deleted=0` **当前在库**才拦截（唯一索引 `IX_StockInventory_tagNo WHERE deleted=0`）
- **建议**：flag=2 改为查 `StockInventory`（与 flag=7 同逻辑），或废弃 flag=2 统一走库存表判断

### TAG-4【低】DTO 无字段校验

- **位置**：`ProdTagDto`（`@Validated` 无实际校验注解）
- **问题**：qty / grossWeight / netWeight 可传 null 或负数，null 会以 "null" 字符串打到 PDF 上
- **建议**：加 `@NotNull` / `@Positive`（或 `@DecimalMin("0")`）

### TAG-5【低】createTime / deleted 依赖数据库默认值

- **位置**：`ProdTagService.add()` 未显式赋值 `createTime`、`deleted`
- **问题**：与表结构默认值耦合，改表结构会静默出问题（如按 createTime 区间查询）
- **建议**：代码显式赋值（`LocalDateTime.now()`、`0`）

### TAG-6【低】无批量打印接口

- **位置**：`ProdTagController.add()` 单标签生成
- **问题**：大批量打印需前端循环调用接口，每个标签一个事务 + 一个 PDF 文件
- **建议**：增加批量生成接口（产品层面需求，需与前端确认）

### TAG-7【低】软删标签无关联保护

- **位置**：`ProdTagService.softDelById()`
- **问题**：未检查标签是否已打托（PalletTag）/已入库（StockInTag），删除后追溯链断裂
- **建议**：删除前检查关联表引用，被引用时拒绝删除

## 第 2 部分：打托（Pallet）

### PAL-1【中】"同一纸箱不能同时在多个托盘"无数据库唯一约束兜底

- **位置**：`PalletService.add()`（第 51 行业务检查）+ `palletTag` 表结构
- **问题**：`PalletTag.tagNo` 无唯一索引（文档只保证 palletNo 唯一），"已打包"检查仅靠业务代码 `listByTagNos`；无并发场景下可用，但数据库层无兜底
- **建议**：`palletTag.tagNo` 加唯一索引（deleted=0 过滤索引），与文档"同一纸箱不能同时在多个托盘"规则对齐
- **状态**：✅ 已生成 SQL（`docs/sql/01-palletTag-tagNo-unique-index.sql`），待 DBA 执行

### PAL-2【低】无托盘删除/解绑接口

- **位置**：`PalletController`（仅 `add` / `findTags` 两个接口）
- **问题**：打托扫错标签后无法解开，只能遗留错误托盘
- **建议**：产品层面确认是否需要解绑/删除功能

### PAL-3【中】flag 语义陷阱：托盘展开场景传 type=1 会全量误报"已打包"

- **位置**：`PalletService.findTagsByPalletNo()` 逐标签调 `prodTagService.findVoByTagNo(tagNo, flag)`
- **问题**：整托操作展开托盘时若传 `type=1`，托盘内**每个标签**都在 PalletTag 中，`assertNotExists` 必然抛"已打包"，整托操作永远失败
- **说明**：`type=1` 只适用于散箱打托前的逐箱扫描，不适配托盘展开场景
- **建议**：接口注释说明 flag 适用场景；或托盘展开时不透传 flag，改为独立校验逻辑

### PAL-4【低】findTagsByPalletNo 逐标签 N 次查询

- **位置**：`PalletService.findTagsByPalletNo()`
- **问题**：托盘内 N 个标签 = N 次 `findVoByTagNo`（每次查视图），性能低
- **建议**：改用批量 `listByTagNos` 一次查出

### PAL-5【低】Pallet / PalletTag 的 createTime / deleted 未显式赋值

- **位置**：`PalletService.add()`（第 60~77 行）
- **问题**：与第 1 部分 TAG-5 同类，依赖数据库默认值
- **建议**：显式赋值，解除与表结构耦合

### PAL-6【中】异常处理吞掉原始异常

- **位置**：`PalletService.add()` catch 块（`throw WebException(e.getMessage())`）
- **问题**：`e.message` 可能为 null（如 NPE），且丢失异常类型与堆栈，排查困难
- **建议**：`throw WebException(e.message ?: "打托失败")`，或保留 cause 直接 rethrow
- **状态**：✅ 已修复（`throw WebException(e.message ?: "打托失败", e)`，保留 cause）

### PAL-7【高】托盘标签打印未实现（仅写 PrintLog）

- **位置**：`PalletService.add()`（第 80~87 行，只有 `printLogMapper.insert`，无 PDF 生成）
- **问题**：流程名"打托打印标签"，但代码未生成托盘标签 PDF/Excel；`PrintLog` 也未设置 `tempId`（模板 ID）；前端打托后拿不到托盘标签文件（接口只返回 palletNo）
- **对照**：`ProdTagService.add()` 有 `generateExcel()`，托盘侧缺失
- **建议**：与产品确认托盘标签是否本期需要；若需要，参照 `ProdTagService.generateExcel` 补齐；暂不做则文档标注
- **状态**：✅ 已确认本期不生成托盘标签 PDF，代码已加注释说明（`PalletService.add()` 第 5 步），后续需要时参照 `ProdTagService.generateExcel` 实现

## 第 3 部分：普通入库（StockIn）

### STK-1【高】防重复检查用错表：查 StockInTag（流水表）而非 StockInventory（库存表）

- **位置**：`StockInService.addByType()`（`stockInTagPlusService.listByTagNos` 判断"已入库"）
- **问题**：`StockInTag` 是入库流水，同一 tagNo 入过库就有记录，且出库时不会被删/置 1（已确认 `StockOutService` 只核销 `StockInventory`）。后果：
  - A：**已出库（deleted=1）的标签无法再次普通入库**，与文档"已出库可重新入库"冲突；
  - B：**退货入库被自己拦死**——`addReturn()` 复用 `addByType()`，任何有入库历史的标签走退货都会报"已入库"，退货功能实际不可用
- **文档规则**：防重复 = `StockInventory.deleted=0` **当前在库**才拦截（唯一索引 `IX_StockInventory_tagNo WHERE deleted=0`）
- **建议**：改为查 `StockInventory.deleted=0`（`stockInventoryPlusService.listByTagNos` 已存在）
- **关联**：与 TAG-3 同根源，修复时一并处理

### STK-2【高】调拨入库（addByTransfer）完全没有防重复检查

- **位置**：`StockInService.addByTransfer()`（直接 resolve → save → addBatch，无任何"已在库"校验）
- **问题**：文档调拨规则明确要求"调入时检查 `StockInventory.deleted=0` 不能重复入库"；若 DB 唯一索引不存在 → 插入两条在库记录库存翻倍；存在 → 抛 500 SQL 异常
- **建议**：与 STK-1 统一加防重复检查

### STK-3【中】StockInventoryService.addBatch 无防重复兜底

- **位置**：`StockInventoryService.addBatch()`（直接 saveBatch 插入）
- **问题**：唯一防线是文档声称的 DB 唯一索引 `IX_StockInventory_tagNo WHERE deleted=0`，需确认是否已建；若没建，STK-1/STK-2 的后果会直接落成脏数据
- **建议**：确认/补建索引（可参照 PAL-1 生成 SQL）

### STK-4【中】普通入库 type=null，与文档"直接入库"不一致

- **位置**：`StockInService.add()` → `addByType(req, null)`，`StockIn.type = null`
- **问题**：文档要求普通入库 `type='直接入库'`；按 type 筛选入库单时普通入库是 NULL（若 DB 列 NOT NULL 会直接插入失败）
- **建议**：统一枚举入库类型（直接入库/退货入库/调拨入库），显式赋值

### STK-5【中】page 查询用 ProdOrder::getCreateTime 过滤 StockIn 表

- **位置**：`StockInService.page()`（`MPJLambdaWrapper<StockIn>().between(ProdOrder::getCreateTime, ...)`）
- **问题**：`StockIn` 无 `prodOrderId` 关联，MPJ 自动 join 语义存疑，条件可能不生效或报错；`StockOutService.page()` 有同样问题（还混用 `StockIn::getReceiptNo`/`StockIn::getId` 查 `StockOut`）
- **建议**：改用 `StockIn::getCreateTime` 过滤，或显式 join 并核实关联条件

### STK-6【低】addByType / addByTransfer 高度重复

- **位置**：`StockInService` 两个方法
- **问题**："校验库位 → resolve → 保存主表+明细+库存"逻辑几乎一样，可抽取公共方法
- **建议**：抽公共私有方法，type 作为参数

### STK-7【低】createTime/updateTime/deleted 依赖 DB 默认值

- **位置**：`StockInventoryService.addBatch()`（只设置 7 个字段）
- **问题**：与 TAG-5 同类；文档 SQL 明确写入 createTime/updateTime=GETDATE()
- **建议**：显式赋值

## 第 4 部分：普通移库（StockMove）

### MOV-1【高】更新库存库位未过滤 deleted，会污染已出库历史记录

- **位置**：`StockInventoryService.editLoc()` / `editLocByTagNo()`（`LambdaUpdateChainWrapper` 仅 `in(tagNo)`，**无 `.eq(deleted, 0)`**）
- **问题**：同一 tagNo 有多条库存记录时（首次入库 deleted=0 + 出库历史 deleted=1），移库会把**所有**记录（含已出库历史）的 locCode/locId 一起改掉，历史追溯失真
- **文档规则**：`UPDATE StockInventory SET ... WHERE tagNo=@tagNo AND deleted=0`（第 4 步）
- **建议**：两个方法都加 `.eq(StockInventory::getDeleted, 0)`

### MOV-2【中】普通移库 type 未赋值（null）

- **位置**：`StockMoveService.add()`（`StockMove().apply { ... }` 无 `type` 字段赋值）
- **问题**：`addByPrep` 有 `type="备料移库"`，普通移库却是 null；文档要求 `type='普通移库'`，按 type 筛选单据时语义不一致
- **建议**：`add()` 补 `type = "普通移库"`
- **状态**：✅ 已修复

### MOV-3【中】未校验目标库位状态（禁用/占用）

- **位置**：`StockMoveService.add()` / `addByPrep()`（仅 `getById` 校验存在）
- **问题**：文档规定库位有 status（空闲/占用/禁用），可移到禁用库位导致货品"丢失"
- **建议**：校验 `LocArchive.status` 非禁用（备料区自动分配逻辑在第 5 部分检查）
- **状态**：✅ 已修复（`add()` 已加 status=="禁用" 校验；`addByPrep()` 库位由备料流程外部传入，不在此处校验）

### MOV-4【低】未校验目标库位与原库位相同

- **位置**：`StockMoveService.add()`
- **问题**：新库位 == 原库位时不提示，生成无意义移库单
- **建议**：相同则提示"目标库位与当前库位相同"或允许（业务确认）

### MOV-5【低】add / addByPrep 高度重复

- **位置**：`StockMoveService` 两个方法
- **问题**：与 STK-6 同类，可抽取公共方法
- **建议**：抽公共私有方法，type 作为参数

### MOV-6【低】createTime / deleted 依赖 DB 默认值

- **位置**：`StockMoveService`（主表/明细未显式赋值）
- **问题**：与 TAG-5 同类
- **建议**：显式赋值

### MOV-7【低】按托盘移库无直接入口

- **位置**：`StockMoveController` / `AddStockIn`（仅 tagNos，无 palletNo 参数）
- **问题**：文档有"按托盘移库"模式，代码需前端先调 `PalletController.findTags` 展开托盘再传 tagNos 间接实现；且展开时注意 PAL-3 的 flag 陷阱
- **建议**：产品确认是否需要 palletNo 直接入口

## 第 5 部分：备料（PrepRecord）

### PRE-1【高】存货编码匹配失败时生成空记录而非报错

- **位置**：`PrepRecordService.add()`（`orderDetails.find { ... }` 后直接 `detailToEntity(detail)`）

- **建议**：`find` 结果判空，为 null 时抛 `WebException("存货编码不在备料指令清单中")`
- **状态**：✅ 已修复（`?: throw WebException(...)` 直接拦截）

### PRE-2【高】packLoc() 硬编码库位 ID（临时方法）

- **位置**：`LocArchivePlusService.packLoc()`（`getById("2026071409485079466907279")`）
- **问题**：注释标注"临时方法"，写死库位主键，不校验库位是否存在/禁用/空闲；文档要求自动分配备料区空闲库位（`locType='备料区' AND status='空闲'`）
- **建议**：改为按 `locType='备料区' AND status='空闲'` 查询分配
- **状态**：⏸ 暂不处理（用户确认）

### PRE-3【中】备料无"已在备料区"重复检查

- **位置**：`StockMoveService.addByPrep()`（仅校验"在库"）
- **问题**：文档要求扫描时检查是否已在备料区避免重复备料；同一标签可反复备料，产生多张备料移库单
- **建议**：备料前查 `StockInventory` 当前库位是否为备料区，是则拒绝

### PRE-4【中】超量备料无控制

- **位置**：`PrepRecordService.add()`（对 `PrepOrderDetail.planQty` 无比对）
- **问题**：文档关键规则"数量控制：防止超量备料"；指令备 100 箱，扫 200 箱也通过
- **决策**：当前不做硬拦截。业务上实际备料数量可能大于指令计划（如指令备100箱，现场有货备150箱），允许超出。代码已加注释说明，后续如需控制可设定允许超出的比例或绝对值
- **状态**：⚠️ 已确认不做拦截，代码已加注释

### PRE-5【中】PrepOrderPlusService.findByNo 未过滤 deleted/status

- **位置**：`PrepOrderPlusService.findByNo()`
- **问题**：查询 `prepNo` 无 `.eq(deleted, 0)`，也未校验 `status IN (0,1)`；已删除/已完成（status=2）的备料单仍可继续备料
- **建议**：加 deleted 过滤 + status 校验
- **状态**：✅ 已修复（加 `.eq(deleted,0)`；status 非 0/1 时抛"已备料完成"）

### PRE-6【中】异常处理吞掉原始异常

- **位置**：`PrepRecordService.add()` catch 块（`e.printStackTrace()` + `throw WebException(e.message)`）
- **问题**：与 PAL-6 同类；`e.message` 可能为 null，堆栈打到 stdout 而非日志框架
- **建议**：`throw WebException(e.message ?: "备料失败", e)`
- **状态**：✅ 已修复（移除 `printStackTrace`，保留 cause）

### PRE-7【低】无托盘备料入口（文档模式 B）

- **位置**：`AddStockOrder`（仅 tagNos）
- **问题**：文档有"按托盘备料"模式，代码无 palletNo 参数
